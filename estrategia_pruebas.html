Este documento recoge las decisiones de QA que guiaron la construcción del entorno simulado y de las

suites automatizadas del repositorio. CineFlex tiene tres capas: un frontend web, un backend REST en

Node.js/Express (autenticación con JWT, inventario de asientos y reservas) y un tercero externo, la

pasarela de pagos del banco. Cada decisión se justifica con el contexto de esta plataforma.

1. Pruebas de integración: Top-Down con Stub de la

pasarela

1.1 Enfoque elegido

Se usa integración Top-Down. El frontend de pagos y el endpoint POST /api/reserva ya están

terminados, y lo único que falta es el componente de nivel inferior (el banco). En Top-Down se prueba

primero desde las capas superiores (UI y API) y cada módulo inferior que todavía no existe se reemplaza

por un Stub. Bottom-Up no encaja aquí: exigiría empezar por el banco, que es justamente lo que no

tenemos, y necesitaría Drivers para simular a los módulos superiores que ya están construidos.

1.2 Diseño del Stub

Principio: el stub debe respetar el mismo contrato que tendrá el banco real (entrada, salida y códigos

HTTP), de modo que el día que haya acceso a la API real solo cambie la implementación, no el código de

CineFlex. Debe ser determinista (la misma tarjeta produce siempre el mismo resultado), no depender de

la red y cubrir tanto el camino feliz como los fallos que el banco real produciría.

Implementación (en backend/server.js, función pasarelaPagosStub). Fragmento simplificado:

   function pasarelaPagosStub({ número, cvv, vencimiento, monto }) {
     const limpio = String(número).replace(/\s|-/g, '');
     if (!/^\d{13,19}$/.test(limpio) || !luhnValido(limpio))
       return { status: 400, body: { aprobado: false, código: 'TARJETA_INVALIDA',
                                     mensaje: 'Tarjeta inválida' } };
     if (limpio === '4000000000000002')
       return { status: 402, body: { aprobado: false, código: 'TARJETA_RECHAZADA' } };
     if (limpio === '4000000000009995')
       return { status: 402, body: { aprobado: false, código: 'FONDOS_INSUFICIENTES' } };
     return { status: 200, body: { aprobado: true, autorizacion: 'AUT-' + Date.now(), monto } };
   }

 Cómo el stub permite probar hoy mismo que CineFlex procesa las ventas:

  - El backend llama a la pasarela a traves de una sola función; es el único punto que habrá que
    reemplazar por la llamada HTTP real al banco.
  - La lógica propia de CineFlex (validar asiento libre, bloquearlo solo si el pago fue aprobado, generar el
    ticket, devolver el código HTTP correcto) se ejecuta completa y es lo que se verifica.
  - Se prueba en dos niveles: API (Postman, prueba negativa con tarjeta falsa) y UI (Selenium: tarjeta
    rechazada TC13 y flujo E2E aprobado TC14/TC15).
  - Regla clave verificada: un pago fallido nunca deja el asiento ocupado (TC13) y un pago exitoso
    siempre lo ocupa (TC15).
 Limitaciones y riesgos. El stub solo es tan fiel como el contrato que se le asigna: si el banco responde
 distinto (por ejemplo, tiempos de espera o 3-D Secure), la integración real puede fallar. Por eso, cuando el
 banco entregue el ambiente de pruebas, se deben ejecutar las mismas pruebas contra la API real y
 agregar pruebas de contrato y de tiempo de espera.

2.2 Estrategia de regresión

Respuesta directa: ante un cambio del color de un botón secundario de la vista de perfil, no se vuelve a

ejecutar toda la suite de la pasarela de pagos. Ese cambio es cosmético, está aislado en la vista de perfil

y no toca lógica de pagos, endpoints ni datos. Ejecutar toda la suite de pagos consumiría tiempo de CI sin

reducir el riesgo real.

Criterio de selección de casos (en orden):

  - Análisis de impacto: qué archivos y módulos toca el cambio, y qué otros módulos dependen de ellos.
  - Riesgo = probabilidad de falla x impacto en el negocio. Pagos y login son de impacto alto (ingresos
    y acceso), por eso siempre están dentro del smoke; un botón de perfil es de impacto bajo.
  - Trazabilidad: cada caso está ligado a un requisito (RF/RNF), lo que permite elegir por area
    modificada.
  - Costo: se prioriza lo barato y rápido (API) en cada push, y lo caro (UI, carga) en ventanas definidas.
